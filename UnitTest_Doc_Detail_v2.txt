TÀI LIỆU CHI TIẾT UNIT TEST CASES
Dự án: Movie Ticket Booking System (Spring Boot 3.4.3, Java 21)
Môn học: Kiểm thử phần mềm — Phần phụ trách: Unit Test
Phạm vi: 90 test case thuộc 13 nhóm chức năng (module backend/src/main/java/com/movieticketbooking/)
Nguồn thiết kế: UnitTest_Design.md (Equivalence Partitioning / Boundary Value Analysis / Decision Table)
Loại tài liệu: Mô tả test case ở mức thiết kế chi tiết — không chứa mã Java/JUnit.
1. Quy ước chung
1.1. Cách đọc một test case
Mỗi test case được trình bày bằng một bảng gồm các mục:
Mục	Ý nghĩa
Mã & Tên	ID duy nhất và tên ngắn gọn của test case
Hàm kiểm thử	Class/phương thức đích (Target Method)
Điều kiện tiên quyết / Mocks	Trạng thái dữ liệu và các dependency được mock trước khi chạy
Dữ liệu đầu vào	Giá trị đầu vào cụ thể (giá trị mẫu, có thể thay bằng giá trị tương đương)
Các bước thực hiện	Trình tự thao tác khi chạy test
Kết quả mong đợi	Giá trị trả về / exception / tương tác (verify) cần đạt
Kỹ thuật	EP (Equivalence Partitioning), BVA (Boundary Value Analysis), DT (Decision Table), Gap test

1.2. Ký hiệu đặc biệt
Ký hiệu	Ý nghĩa
[Known Limitation]	Test case rơi vào GAP/DEFECT đã biết. *Kết quả mong đợi* được viết theo hành vi thực tế hiện tại của code, không phải hành vi lý tưởng. Nhóm quyết định giữ nguyên và ghi nhận trong Test Report.
[Current Behavior]	Hành vi hiện tại của code đối với dữ liệu null (thiếu null-guard) nhưng không thuộc 4 Known Limitation chính thức. Test ghi nhận hành vi thực tế.
verify never	Mock tương ứng không được gọi trong luồng của test.

1.3. Nguyên tắc chung khi thực thi
•Unit test chạy cô lập: mọi dependency (Repository, PasswordEncoder, AuthenticationManager, RedisTemplate, service phụ thuộc, dịch vụ gửi email…) đều được mock; không kết nối DB/Redis thật.
•Các test phụ thuộc thời gian (TICKET-BOOK-05, TICKET-CANCEL-07, AUTH-REF-05, CLEAN-06) hiện không có `Clock` được inject trong code. Do đó, dữ liệu thời gian được dựng với khoảng đệm đủ lớn (ví dụ ±5 phút) so với now; không assert chính xác tại đúng thời điểm biên (mili-giây) để tránh test không ổn định (flaky).
•Các giá trị trong cột *Dữ liệu đầu vào* là giá trị mẫu; message exception được so khớp theo đúng chuỗi trong code khi design đã nêu cụ thể, các trường hợp còn lại chỉ assert loại exception (và nội dung message nếu code có).

3.3. AuthServiceImpl.forgotPassword / resetPassword — nhóm AUTH-OTP (7 TC)

3.4. JwtService — nhóm JWT (10 TC)
Mô tả logic: Access token ký bằng secret Base64; subject = userDetails.getUsername(); có issued-at và expiration = now + jwtExpiration. isTokenValid = subject trùng username và token chưa hết hạn; các lỗi parse/signature/Base64/hết hạn không bị service bắt (exception của JJWT được truyền ra). Refresh token = 2 UUID nối bằng -, không chứa claims.
Thiết lập chung: Khởi tạo JwtService thật (không mock); inject secret Base64 hợp lệ (đủ độ dài khóa HMAC ≥ 256 bit), jwtExpiration = 3600000 ms (1 giờ) và refreshExpiration bằng cấu hình/giá trị mặc định. UserDetails mẫu: username = user@mail.com.
JWT-01 — Tạo và parse access token
Mục	Nội dung
Hàm kiểm thử	JwtService.generateToken(UserDetails), extractUsername(token), extractClaim(token, fn)

•Path coverage: Kiểm tra các đường đi độc lập/quan trọng trong CFG; đường đi không khả thi phải ghi rõ.
•Cyclomatic complexity: Ước lượng số đường đi độc lập trong CFG; giá trị chính xác cần xác nhận bằng CFG/JaCoCo.

•ROOM-06: Room.createSeats thiếu kiểm tra columns <= 0. Đây là Known Limitation vì guard thiếu đã được xác nhận chính thức.
•SHOWTIME-06: createShowTime không kiểm tra suất chiếu trùng/giao. Đây là Known Limitation vì thiếu overlap branch trong source.

•AUTH-REG-04, AUTH-LOGIN-04, TICKET-CANCEL-04: các lỗi null tương ứng là Current Behavior, không thuộc 4 Known Limitation.
